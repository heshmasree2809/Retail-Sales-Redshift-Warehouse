# Retail Sales Data Warehouse (Amazon Redshift Serverless)

A star-schema warehouse that extends a retail ETL pipeline (S3 → Glue/PySpark → curated Parquet).
It loads the curated zone into **Amazon Redshift Serverless**, validates and quarantines bad rows,
merges good rows idempotently by date, runs analytical SQL, and gates the run on data-quality checks.
All data is **synthetic** (generated by `src/rdw/generate.py`); no real retailer data is used.

```
raw CSV ─► S3 ─► Glue PySpark (existing) ─► curated Parquet (S3, date-partitioned)
                                                  │
        Step Functions ───────────────────────────┤
          1 CreateSchema   (idempotent DDL)       ▼
          2 LoadFromS3     COPY ─► dims + stg_sales
          3 Transform      validate ─► sales_rejects ; delete+insert by date ─► fact_sales
          4 Maintenance    ANALYZE
          5 QualityGate    11 checks, any failure fails the run
                                                  │
                                    SQL marts + dashboard (HTML or QuickSight)
```

## Data model

| Table | Grain / role | Distribution / sort |
|---|---|---|
| `fact_sales` | one row per order line: quantity, price, discount, revenue, cost, profit | `DISTKEY(product_key)`, `SORTKEY(date_key)` |
| `dim_date`, `dim_product`, `dim_store` | small, joined by every query | `DISTSTYLE ALL` |
| `dim_customer` | larger dimension | `DISTKEY(customer_key)` |
| `stg_sales` | landing table for the Parquet, carries `reject_reason` | `DISTSTYLE EVEN` |
| `sales_rejects` | quarantined rows per batch (reason recorded) | `DISTSTYLE EVEN` |

```bash

```

The demo uses the same `03_transform.sql`, `05_quality_checks.sql` and `06_analytics.sql` that run on Redshift.
SQLite proves the SQL logic. It says nothing about Redshift performance.

## Deploy to AWS

Prerequisites: AWS CLI v2 configured, Python 3.12, permissions to create IAM roles, S3, Lambda, Step Functions, Redshift Serverless.

```bash
STACK=retail-dw AWS_REGION=ap-south-1 ./scripts/deploy.sh     # stack name must be lowercase
ROWS=1000000 ./scripts/run_pipeline.sh                        # generate, upload, run, wait for result
make bench WORKGROUP=retail-dw-wg                             # tuned vs untuned timings -> results/benchmark.md
make dashboard WORKGROUP=retail-dw-wg                         # build/dashboard.html from Redshift
./scripts/teardown.sh                                         # delete everything when you are done
```

To run your existing Glue job first: `INPUT='{"glue_job_name":"your-job"}' ./scripts/run_pipeline.sh`
(the Glue output must keep the column order in `src/rdw/generate.py`, because Redshift `COPY` maps Parquet by position).

**Cost:** Redshift Serverless bills for compute while queries run, plus storage. `deploy.sh` sets a daily
usage limit that deactivates the workgroup when exceeded and uses the smallest base capacity by default.
Run `teardown.sh` after you record your results. Check current AWS pricing and free-trial credits before deploying.

**QuickSight (optional):** create a dataset from the Redshift tables (`fact_sales` joined to the dimensions), or use the
queries in `sql/06_analytics.sql` as custom SQL. `src/rdw/dashboard.py` builds a dependency-free HTML version.

## What the SQL does

- `03_transform.sql`: flags rows (null keys, non-positive quantity, unknown date/product/store/customer, duplicate order lines),
  copies them to `sales_rejects` with the batch id, then **deletes and re-inserts by date** so re-running a batch never double counts.
- `05_quality_checks.sql`: orphan foreign keys, duplicates, negative amounts, revenue and profit formulas, staging-to-fact row reconciliation, and a 5% reject-rate gate.
- `06_analytics.sql`: top 3 products per store (`RANK`), month-over-month growth (`LAG`), 7-day moving average (window frame),
  margin by category, repeat-purchase rate, and a Pareto analysis of the top 20% of products.

## Design decisions and trade-offs

- **Why a star schema:** facts are additive and dimensions are small, so every analytical query is a fact scan plus cheap dimension joins, and dimensions with `DISTSTYLE ALL` avoid redistribution.
- **Grain:** one row per order line, so quantity, revenue, cost and profit stay additive and can roll up to order, store, product or day.
- **Distribution and sort keys:** `product_key` spreads a large fact evenly and co-locates product rollups; `date_key` as sort key lets date-range filters skip blocks. `make bench` compares against a copy with `DISTSTYLE EVEN` sorted by load order.
- **COPY vs Spectrum:** this loads the data into Redshift for repeatable performance. Spectrum would query the S3 files in place, which is cheaper to start and slower per query.
- **Money columns:** `DECIMAL` in the fact table; the staging and dimension columns are `DOUBLE PRECISION` because Parquet doubles do not `COPY` into `DECIMAL` reliably.
- **Idempotency:** dimensions are refreshed by `TRUNCATE` + `COPY`; the fact is replaced by date, and rejects are keyed by batch id.

## Known limitations

- Foreign keys are informational in Redshift; integrity is enforced by the transform and verified by the checks, not by the database.
- Dimensions are full refreshes (no slowly changing dimension history).
- One batch is loaded at a time; there is no schedule. Add an EventBridge rule to run the state machine on a timer.
- Customer attributes are synthetic and contain no personal data.
- The CloudFormation template, Lambda runner and Data API code have unit tests with a fake client but **have not been run against a live AWS account by the author of this scaffold**; expect to fix small environment-specific issues on first deploy (subnets/VPC, permissions, region limits).
